# 2.5 自建 API 中转站

> 本文由 **卡网大全 [cardnav.xyz](https://cardnav.xyz)** 提供。

自建 API 中转站通过统一接口连接上游模型与内部工具，适合需要集中管理访问密钥、额度和调用记录的开发者或团队。部署前应确认上游授权、接入方式和使用范围；能够完成技术接入，不代表订阅允许共享、转售或转换为 API 服务。

## 核心优势

- **额度可集中管理**：可以把官方额度统一分配给多个工具、项目或成员。
- **成本可控**：团队内部可以按需限制额度、记录调用量和控制预算。
- **接入灵活**：可以对接内部应用、代码助手、自动化脚本和多个客户端。
- **可做权限控制**：比直接把原始账号或主 Key 分给别人更容易管理。

## 局限与风险

- **需要运维能力**：服务器、域名、HTTPS、日志、限速、密钥管理都需要自己维护。
- **上游限制仍然适用**：调用频率、使用人数和功能范围受上游配额与授权约束，中转程序不能解除这些限制。
- **权限管理责任增加**：成员密钥泄露或滥用可能耗尽额度，应设置独立权限和用量限制。
- **安全边界要清楚**：所有请求都会经过中转服务，必须保护好日志和密钥。

## 适合人群

- 具备 Linux、Docker、反向代理和 API 运维经验的开发者
- 需要统一管理模型额度和 Key 的小团队
- 需要将模型接入内部工具、自动化流程或多个客户端的开发者

## 是否值得自建

### 适合自建的情况
- 团队需要统一分发 Key、限制额度和查看调用量
- 内部工具需要稳定接入多个模型或多个客户端

### 可以暂缓自建的情况
- 只是个人轻量使用，优先考虑官方账号或成熟中转站
- 没有服务器、HTTPS、日志、安全和异常处理经验时，需要将维护时间和故障处理成本纳入预算

### 关键边界
- 不要直接共享主账号或主 Key
- 尽量给成员分发独立 Key，并保留用量和异常记录

## Sub2API
<!-- badge="订阅转换" icon="api" -->

将订阅或账号凭证转换为 OpenAI 兼容接口，适合已有上游账号、需快速接入 API 客户端的用户。

### 适合场景
- 将已有账号或订阅额度接入 Chatbox、Cherry Studio、代码插件等工具
- 以较低部署成本验证中转流程

### 注意事项
- 部署前确认账号来源、上游条款和订阅允许的使用范围
- 不向团队成员暴露主账号、主 Key 或敏感日志

[查看项目](https://github.com/Wei-Shaw/sub2api)

## CliProxyAPI
<!-- badge="CLI 代理" icon="vps" -->

面向 CLI 与 Agent 的代理接口，可将模型接入命令行工具、开发工作流和内部自动化任务。

### 适合场景
- 代码助手、命令行工具与 Agent 工作流统一接入模型
- 集中管理团队访问密钥、额度与调用入口

### 注意事项
- 部署时配置 HTTPS、访问密钥、限速与日志策略
- 长期使用前，以真实开发任务测试稳定性、兼容性与额度消耗

[查看项目](https://github.com/router-for-me/CLIProxyAPI)

## 实操步骤

1. 先选购海外云服务器，具体主机选择可以参考 [云服务器推荐](./322-tool-vps.md)。
2. 准备官方账号、可用额度或上游 API Key，并确认其使用条款和风控边界。
3. 从上方推荐项目里选择更适合你使用场景的中转程序。
4. 配置 HTTPS、访问密钥、额度限制、日志保留策略和异常告警。
5. 给团队成员分发独立 Key，不要直接共享主账号或主 Key。
6. 定期检查调用量、失败率、异常请求和上游账号状态。

## 使用建议

自建中转的投入包括服务器、维护时间、安全管理和上游费用。只有统一接入、成员权限或调用管理能带来实际收益时，才值得承担这些成本；个人轻量使用可以先选择官方服务或经过核验的托管服务。
